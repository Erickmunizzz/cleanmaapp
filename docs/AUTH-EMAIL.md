# CleanMa authentication email and employee invitations

There are two independent sending paths:

- **Supabase Auth custom SMTP** sends owner confirmation, password resets and the Cleaner one-time sign-in code. The public Auth settings confirm registration and email confirmation are enabled. SMTP, redirect allow-list and email template settings are not exposed by that endpoint.
- **Resend through the app’s Vercel API** sends employee invitations. The owner initiates invitations from **Employees**. The app verifies the active employee and workspace, provisions a linked Cleaner login if needed, and sends the Cleaner URL and a temporary password. The Cleaner must set their own password before accessing the workspace. When the Resend variables are missing, the invitation intentionally stays pending. After configuration, retry the same invitation from **Employees** rather than creating another employee record.

## Required dashboard checks

1. In **Resend → Domains**, add and verify a dedicated transactional sending subdomain, for example `auth.cleanmaapp.com`. Add the exact SPF, MX and DKIM records Resend lists for that subdomain and its return-path at the DNS provider. Leave the root Zoho MX in place for receiving `contact@cleanmaapp.com`, and do not create a second SPF record at the same hostname. Turn off click tracking on Auth email links.
2. In **Supabase → Authentication → Email → SMTP Settings**, enable custom SMTP. For Resend, host `smtp.resend.com`, port `587` (STARTTLS), user `resend`, SMTP password a Resend sending API key, name `CleanMa` and verified sender such as `no-reply@auth.cleanmaapp.com`. Use a separate sending key from the employee API where possible. Do not turn off confirmation. Supabase’s built-in mailer is not a production alternative; it only sends to pre-authorized project-team addresses.
3. In **Supabase → Authentication → URL Configuration**, set **Site URL** to `https://cleanmaapp.com`. Allow the exact production return URLs emitted by the app: `https://cleanmaapp.com/admin/login?confirmed=1` for new-owner confirmation, `https://cleanmaapp.com/auth?mode=recovery` and `https://cleanmaapp.com/auth?mode=recovery&role=cleaner` for the two reset links, and `https://cleanmaapp.com/cleaner.html` for the standalone Cleaner sign-in link. Retain required existing links; avoid a broad production wildcard. In **Email Templates**, ensure Confirm signup and Reset password preserve `{{ .ConfirmationURL }}` so the requested destination is carried by the verification link. Do not use the URL fragment as part of the allow-list: it is added by Supabase only after verification.
4. In **Vercel → cleanmaapp app project → Settings → Environment Variables**, add `RESEND_API_KEY` (sensitive, sending access only for the verified domain) and `CLEANMA_INVITE_FROM` (for example, `CleanMa <invites@auth.cleanmaapp.com>`) to **Production** if not already configured via inherited variables. Both names are server-only. Redeploy the same app project, then use **Employees → Invite All** for already-pending invites when you are ready to send them.
5. Verify Zoho inbound separately. Public DNS currently returns `0 cleanmaapp.com.` as an apex MX alongside Zoho `10 mx.zoho.com.`, `20 mx2.zoho.com.` and `50 mx3.zoho.com.`. The lower number wins; if Zoho should be the only inbound provider, check the correct MX values in **Zoho Mail Admin Console → Domains → cleanmaapp.com → Email Configuration → MX** and remove the competing apex MX only once the intended routing is confirmed. Verify configured DKIM, plan a DMARC policy, and confirm an authorized external test actually arrives in `contact@cleanmaapp.com`. Do not point root MX at Resend for these outbound messages.

## Launch acceptance tests

Use authorized test inboxes, preferably in a separate environment before public rollout. Confirm a new owner’s email link and first sign-in; request and complete both role-specific password resets (also check an expired link); invite a test Cleaner and verify the email arrives and the password change unlocks access. Check the relevant provider’s delivery logs as well as the inbox. A successful API response only confirms the provider accepted the invitation, not that the inbox received it.
